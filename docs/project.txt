# Project Speedboat: Universal Volunteer Computing Blueprint (2026)

## 1. Overview Architecture: The "Modular Multi-Tier" Model
Project Speedboat is a modern, modular volunteer computing platform separating scientific logic from untrusted infrastructure.

* **Master Node (Orchestrator):** Manages NATS work queues, automates container image baking and WASM compilation, and validates results.
* **Message Bus (NATS.io):** A real-time system that punches through firewalls and NATs using native WebSocket and TCP connections.
* **Primary Worker (Native Go Agent):** A portable single-binary client (`agent.exe` / `.app`) powered by Wails v3 or a headless CLI. It dynamically switches between **Heavy Mode** (rootless `crun`/`apptainer`) and **Lite Mode** (embedded **wazero** runtime).
* **Secondary Worker (Browser WASM):** A zero-install fallback executing tasks inside a browser tab via Web Workers and `nats.ws`.

---

## 2. The Volunteer Experience: Single-Binary Zero Friction

### The Windows "Holy Grail" (`agent.exe`)
Windows adoption typically fails due to driver conflicts, virtualization requirements, and update loops. Speedboat solves this through pure Go static linking:
* **Zero External Dependencies:** No Docker Desktop, no WSL2, no VirtualBox, and no C++ redistributables or CGO required.
* **Dual Execution Path:**
  * **Heavy Mode:** If a container runtime (`crun`/`podman`) is present, the agent runs native OCI/Apptainer containers with full hardware access (GPU/AVX-512).
  * **Lite Mode (Embedded `wazero`):** If no container engine exists, the agent executes `.wasm` payloads directly inside its own memory space using **wazero** (zero-dependency pure Go WebAssembly runtime).
* **Silent In-Memory JIT:** `wazero` compiles `.wasm` bytecode in-memory to native x86-64/ARM64 machine code, achieving 85–90% of native speed with no browser overhead.
* **UI Options:** Available as a lightweight **Wails v3** desktop GUI (using the OS native WebView) or a minimal system tray/terminal app.

---

## 3. WASM Compilation Strategy: Direct vs. container2wasm (c2w)
For Lite Mode and Browser workers, the Master Node uses a two-tier strategy to generate `.wasm` payloads from scientific code:

### Direct Cross-Compilation (Targeted WASI)
* **How it works:** Compiles code directly to WebAssembly bytecode via LLVM, Emscripten, or Pyodide.
* **Performance:** Minimal overhead (~10–15% slowdown relative to native speed via JIT).
* **Payload Size:** Highly optimized, compact artifacts (1 MB – 30 MB).
* **Best for:** High-throughput, performance-critical compute tasks where CPU efficiency matters.

### container2wasm (c2w Full Emulation & Debugging Target)
* **How it works:** Converts an existing Linux Docker image directly into a `.wasm` file by packaging the entire container root filesystem (OS, dynamic `.so` libraries, binaries) together with a software CPU emulator (such as Bochs, TinyEMU, or QEMU).
* **The Fallback Penalty:** A $5\times$ to $20\times$ software CPU emulation slowdown makes long-running scientific simulations impractical. Running failed WASI targets through c2w wastes volunteer compute cycles and electricity; it is strictly a rapid prototyping and debugging target, not a production compute tier.
* **Payload Size:** Substantially larger artifacts (50 MB – 300 MB+ including rootfs).
* **Best for:** Functional verification and fallback debugging for legacy C++/Fortran binaries or complex dynamic libraries that fail native WASI cross-compilation.

### WASM Strategy Comparison

| Feature | Direct Cross-Compilation (LLVM / WASI) | container2wasm (Full Container to WASM) |
| :--- | :--- | :--- |
| **Compute Overhead** | ~10–15% slowdown (Near-native JIT) | ~5x–20x+ slowdown (Software CPU emulation) |
| **Role in Platform** | Production Lite/Browser Compute | Rapid Debugging / Prototyping Target Only |
| **Artifact Size** | Small (1 MB – 30 MB compiled logic) | Large (50 MB – 300 MB+ including Linux rootfs) |
| **Legacy/Fortran Support** | Requires LLVM Flang / cross-toolchains | Works out-of-the-box (any Docker image) |
| **Scientist Friction** | Needs build-target configuration | Zero (reuses existing Docker image directly) |
| **Memory Footprint** | Low (only allocated logic memory) | Higher (RAM for emulated OS boot + workload) |

## 4. Hardware Acceleration: GPU Compute Parity
Modern scientific workloads (Folding@home molecular dynamics, cryo-EM processing, LLM fine-tuning) run almost exclusively on accelerated hardware:

* **Heavy Mode (Native Acceleration):** Direct access to NVIDIA CUDA, AMD ROCm, and Intel oneAPI via host driver pass-through in rootless containers.
* **Lite & Browser Mode Roadmap:** To avoid remaining purely CPU-bound, Lite Mode targets WebGPU and WASI-NN bindings to execute tensor and matrix workloads inside WASM runtimes without requiring full container engines.

---

## 5. Scientist UX: "Math-to-Grid" Pipeline
Scientists write scientific code without needing to learn DevOps, cross-compilation, or distributed systems.

* **Auto-Baking:** The scientist provides scientific source files (`logic.py`, `.cpp`, `.f90`, or `.rs`) and a `project.yaml`. The Master Node auto-builds OCI container images and compiles WASM binaries.
* **The Standard Stream Contract:**
  * **Generator (Python):** Emits a JSON array of task specifications to `stdout`.
  * **Logic (Any Language):** Reads a task JSON from `stdin` and writes the calculated JSON result to `stdout`.
  * **Reducer (Python):** Collects verified result batches via `stdin` to aggregate the final research dataset.

---

## 6. Security & Isolation: "Zero-Trust Sandboxing"
All computations execute inside strict technical boundaries to prevent system compromise or data exfiltration.

* **Container Isolation (Heavy Mode):** Unprivileged, rootless execution using Linux user namespaces, read-only root filesystems, seccomp filters, and disabled networking.
* **In-Memory Memory Sandbox (`wazero` Lite Mode):** The WASM payload is confined to its allocated memory block. It has zero access to host files (`C:\Users\...`), the Windows Registry, peripherals, or host network interfaces.
* **Trap Error Handling:** If scientific code crashes or attempts an out-of-bounds memory access, `wazero` raises a runtime trap, terminating only the isolated task while keeping the host system completely stable.

---

## 7. Result Verification & Anti-Cheating

Because volunteer nodes are untrusted and leaderboard incentives can encourage spoofing, integrity checks are mandatory:

* **Redundancy Verification:** Master dispatches identical task payloads to 3 distinct workers.
* **Deterministic Consensus & Floating-Point Handling:**
  * *The Flaw:* Floating-point arithmetic ($FP32 / FP64$) varies across architectures (x86-64 vs. ARM64 vs. WASM software floats). Exact bit-for-bit string comparisons cause false negatives across heterogeneous nodes.
  * *The Mitigation:* Majority consensus enforces deterministic compilation flags (e.g., `-ffp-contract=off`, `-fno-fast-math`), fixed-point math where viable, or domain-specific epsilon tolerance comparisons in the Reducer.
* **Majority Consensus:** Results are accepted into the reducer once 2 out of 3 outputs agree within defined tolerance thresholds.
* **Spot-Checking:** The Master periodically injects deterministic "trap tasks" with pre-calculated outputs to detect and ban bad actors.

## 8. Execution Matrix

| Capability | Browser (WASM) | Lite Mode (`wazero` Agent) | Heavy Mode (`crun` / Apptainer) |
| :--- | :--- | :--- | :--- |
| **Prerequisites** | Web Browser | `agent.exe` (Single file) | Container Runtime / Linux |
| **Performance** | ~80% Native | ~85–90% Native (JIT) | 100% Native + GPU / AVX-512 |
| **Acceleration** | WebGPU (Targeted) | CPU / WASI-NN (Roadmap) | Full CUDA / ROCm / AVX-512 |
| **WASM Engine** | Browser Web Worker | Embedded `wazero` (JIT) | N/A (OCI Container Runtime) |
| **Isolation** | Browser Sandbox | Software Memory Jail | Linux Kernel Namespaces / Seccomp |
| **Persistence** | While tab is active | Background process / System tray | System service / Background daemon |
| **Networking** | `nats.ws` (WebSocket) | NATS TCP / WebSocket | NATS TCP |
